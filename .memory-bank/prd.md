## Product Summary

Продукт — SvelteKit web-приложение для небольшого учебного центра. Его основной
интерфейс — эластичный календарь, в котором учебные дни занимают больше места,
чем неучебные. Один учебный день объединяет содержание урока, домашнюю работу,
обсуждение, посещаемость и связанные с учеником финансовые состояния.

Приложение разделяет общий контекст класса и личный контекст ученика. Первый
Admin входит по созданным локальной CLI-командой email/password credentials;
Telegram Login и Google OAuth остаются доступными provider flows. Роли и доступ
назначаются системой и учебным центром, а не выбираются пользователем
самостоятельно.

Каждая защищённая страница также использует единый navigation shell с
hamburger-кнопкой в правом верхнем углу. Через него пользователь переходит к
главной, доступным классам, статистике и профилю либо выходит из приложения.
Статистика является отдельным обзорным слоем с таблицами учеников, учителей и
классов; она не заменяет и не меняет календарь, уроки, личный контекст или
финансовый сценарий.

## Goals

- Сделать учебный день основной точкой организации работы центра.
- Дать каждой роли быстрый доступ только к относящемуся к ней общему и личному
  контексту.
- Сделать ритм обучения и состояния дней считываемыми непосредственно из
  календаря.
- Сохранить связанные с уроком материалы и общение в одном месте.
- Вести прозрачный денежный баланс ученика с воспроизводимым распределением
  платежей.
- Предоставить первый локальный Admin-доступ по email/password и сохранить
  вход через Telegram и Google без самовольного получения роли.
- Дать пользователю единый короткий путь к основным разделам приложения через
  постоянное меню.
- Дать разрешённым пользователям простой табличный обзор учеников, учителей и
  классов с сортировкой по столбцам.

## Non-goals

- Функции полноценной школьной информационной системы, государственная
  отчётность и школьная иерархия.
- Платёж, выраженный количеством уроков.
- Ручное распределение каждого платежа как основной сценарий.
- Публичное отображение персональных оценок всему классу.
- Финансовая раскраска общего календаря класса в MVP.
- Классическая семиколоночная сетка или второй равноправный режим как основной
  календарь.
- Самостоятельный выбор пользователем роли или получение доступа только по
  факту входа через внешний provider.
- Self-registration, password reset/recovery, email verification, MFA,
  password history и самостоятельная смена/выдача password credentials.
- Пересмотр основного календаря, уроков, личного контекста или финансового
  ledger в рамках добавления меню и статистики.
- Сложная BI-панель с графиками, конструктором отчётов и расширенной системой
  фильтров на первом шаге.
- Глобальное администрирование нескольких центров, cross-center статистика и
  управление филиалами в MVP.

## Users / Actors

### Admin

- Создаёт сотрудников, классы и связанные с ними аккаунты.
- Назначает роли и членство в классах.
- Работает внутри собственного Center и видит статистику только этого Center.
- Имеет административный доступ к данным собственного Center только через
  серверно разрешённые операции.
- Может заносить, исправлять и отменять платежи для разрешённых учеников и
  классов собственного Center.
- Выдаёт одноразовые приглашения для первичной привязки внешней identity.

### Teacher

- Работает только с назначенными ему классами и их учениками.
- Пока назначен классу, видит его полную прошлую учебную и личную историю,
  включая комментарии и чат до его назначения.
- Ведёт календарь, содержание уроков, посещаемость, ДЗ и оценки.
- Видит персональные оценки учеников назначенного класса.
- Может занести новый платёж только для ученика назначенного класса, но не
  может исправить или отменить его.

### Student

- Видит общий календарь своих классов и собственный личный календарь.
- Отмечает выполнение своего ДЗ, пишет разрешённые комментарии и сообщения,
  оставляет реакции.
- Видит только собственные оценки и финансовые состояния.

### Parent

- Видит общий календарь класса ребёнка и личный календарь связанного ученика.
- Участвует в разрешённых комментариях, чате и реакциях.
- Видит оценки и финансовые состояния только связанного ученика.

## Functional Requirements

### Authentication and Account Binding

- **FR-AUTH-001:** MVP MUST поддерживать браузерный вход по email/password для
  аккаунта с password credential; существующие Telegram Login и Google OAuth
  flows сохраняются.
- **FR-AUTH-002:** Для пустой базы оператор MUST локально запустить server-only
  CLI, которая в одной транзакции создаёт первый внутренний Admin-аккаунт и его
  password credential. Bootstrap разрешён только когда `accounts` пуст; email
  хранится как unique normalized `trim().toLowerCase()`, а пароль принимается
  только скрытым интерактивным prompt и никогда не передаётся через argv, не
  логируется и не хранится plaintext. После входа этот Admin создаёт первый
  Center и получает его membership атомарно.
- **FR-AUTH-003:** При открытии действующей invite-ссылки пользователь MUST
  выбрать Telegram или Google; подтверждённая provider identity привязывается к
  указанному внутреннему аккаунту.
- **FR-AUTH-004:** Пользователь MUST NOT самостоятельно назначать или менять
  роль в процессе входа.
- **FR-AUTH-005:** Второй provider MAY быть добавлен к тому же аккаунту только
  из уже авторизованного профиля после повторного подтверждения текущей сессии.
- **FR-AUTH-006:** Одна provider identity MUST NOT быть одновременно привязана
  к нескольким внутренним аккаунтам.
- **FR-AUTH-007:** Истёкшее, отозванное или уже использованное приглашение MUST
  завершаться понятным отказом без создания нового аккаунта.
- **FR-AUTH-008:** Недоступность одного provider MUST NOT давать обходной путь к
  роли или чужому внутреннему аккаунту; пользователь может использовать только
  provider, уже привязанный к его аккаунту, либо действующее приглашение.
- **FR-AUTH-009:** После успешного provider callback или email/password входа
  для Admin система MUST открыть защищённую Admin-поверхность. До создания
  первого Center Admin может открыть только защищённую форму создания Center;
  после создания Center доступ к его операциям требует server-side membership.
- **FR-AUTH-010:** Password credential MUST использовать Node built-in
  `scrypt` с отдельной cryptographically random salt и `timingSafeEqual`;
  plaintext password MUST NOT сохраняться. Неизвестный email и неверный пароль
  MUST давать один generic invalid-credentials результат без сессии и без
  раскрытия существования аккаунта.
- **FR-AUTH-011:** Admin MUST иметь возможность атомарно создать teacher,
  student или parent с normalized email/password и membership собственного
  Center; parent требует существующего student link. Такой аккаунт входит через
  существующий `/login`; invite/provider flow сохраняется.

### Global Navigation and Statistics

- **FR-NAV-001:** Каждая защищённая страница MUST содержать единый hamburger-
  элемент в правом верхнем углу, открывающий пункты «Главная», «Классы»,
  «Статистика», «Профиль» и «Выйти».
- **FR-NAV-002:** Переход «Классы» MUST показывать только классы, доступные
  текущему пользователю по серверно определённому membership или assignment
  scope.
- **FR-NAV-003:** Пункт «Статистика» MUST открывать три направления: «Ученики»,
  «Учителя» и «Классы». Доступ к каждому направлению и строки таблиц MUST
  определяться серверной ролью и scope, а не только видимостью пунктов в UI.
- **FR-NAV-004:** «Выйти» MUST завершать текущую server session и возвращать
  пользователя на страницу входа.
- **FR-NAV-005:** Admin MUST видеть статистику собственного Center. Teacher
  MUST видеть только статистику, связанную с назначенными классами; Student и
  Parent MUST NOT видеть center-wide статистические реестры.
- **FR-STAT-001:** Таблица «Ученики» MUST поддерживать столбцы: ФИО, дата
  регистрации, класс, родитель, учитель, платёжеспособность, посещаемость в
  процентах и учебное заведение.
- **FR-STAT-002:** Таблица «Учителя» MUST поддерживать столбцы: ФИО, дата
  регистрации, класс, посещаемость в процентах, учебное заведение и количество
  учеников среди всех классов учителя.
- **FR-STAT-003:** В ячейке классов учителя несколько классов MUST показываться
  с новой строки; при сортировке по этому столбцу MUST учитываться первый класс
  из списка.
- **FR-STAT-004:** Таблица «Классы» MUST поддерживать столбцы: название класса,
  учебное заведение, количество учеников и учитель, который его ведёт.
- **FR-STAT-005:** Каждый столбец статистической таблицы MUST поддерживать
  выбор направления сортировки, а активное направление MUST быть понятно из
  заголовка. Текстовые поля сортируются по алфавиту, даты — хронологически,
  проценты и числовые значения — по числовому значению.
- **FR-STAT-006:** Платёжеспособность ученика MUST отображаться в процентах как
  доля своевременно оплаченных Payment Allocation от общего числа учитываемых
  allocations; аванс и нераспределённая часть платежа не считаются.
  Платёж считается внесённым вовремя только если его фактическая дата
  предшествует фактической дате урока, к charge которого он allocated; остальные
  учитываемые allocations
  считаются просроченными. При отсутствии платежей значение MUST быть `0%`, а
  `100%` MUST означать, что все учитываемые платежи внесены вовремя.
- **FR-STAT-007:** Посещаемость ученика MUST строиться по отметкам `present` и
  `absent`, внесённым teacher в день урока через список учеников класса, и
  рассчитываться по всем проведённым урокам, а не только по урокам с отдельной
  отметкой.

### Center, Classes, and Scheduling

- **FR-ORG-001:** Admin MUST управлять учителями, классами, учениками,
  родителями и их связями внутри собственного Center.
- **FR-ORG-006:** Bootstrap Admin MUST иметь возможность создать ровно один
  Center и задать ему одно название учебного заведения. Операция MUST
  атомарно создать Center и Admin membership; после этого повторное создание
  Center через bootstrap запрещено.
- **FR-ORG-002:** При создании класса MUST выбираться режим `individual` или
  `group`.
- **FR-ORG-003:** Admin MUST иметь возможность создать повторяющееся расписание
  класса, из которого создаются запланированные уроки. Schedule form сохраняет только scoped
  `{startDate,endDate,weekdays}` до успешного создания; controls показывают
  `dd/mm/yyyy`, а Form Data и storage используют ISO `YYYY-MM-DD`.
- **FR-ORG-004:** Admin и назначенный teacher MUST иметь возможность добавить,
  перенести или отменить отдельный урок без изменения остальных повторений.
  Диапазон без выбранного weekday MUST отклоняться до изменения Schedule или
  Lesson state.
- **FR-ORG-005:** Перенос MUST сохранять identity урока и связанный контекст, а
  не создавать несвязанные старую и новую записи. Новое recurring schedule
  заменяет только overlapping `planned` lessons; overlap с `completed` или
  `cancelled` отклоняется атомарно.

### Elastic Calendar

- **FR-CAL-001:** Основной календарь MUST отображать каждую неделю отдельной
  эластичной строкой.
- **FR-CAL-002:** Дни с уроками MUST быть шире неучебных дней; вертикальное
  выравнивание одинаковых дней недели между строками не требуется.
- **FR-CAL-003:** Стандартный date picker MUST обеспечивать точный переход к
  нужной дате.
- **FR-CAL-004:** Смысл состояния MUST NOT передаваться только цветом; цвет
  дублируется символом, подписью или другой различимой формой.
- **FR-CAL-005:** Календарь класса и личный календарь ученика MUST использовать
  одну временную основу и взаимные переходы, но разные разрешённые данные.

### Shared and Personal Day Forms

- **FR-DAY-001:** Общая форма учебного дня MUST содержать тему урока, описание
  практической работы и домашнее задание.
- **FR-DAY-002:** Личная форма дня MUST показывать общие материалы урока и
  персональные данные только выбранного ученика.
- **FR-DAY-003:** В общем контексте пользователь MAY оставить по одному
  редактируемому комментарию от своего аккаунта к каждому полю.
- **FR-DAY-004:** Комментарий MUST показывать автора и время последнего
  изменения.
- **FR-DAY-005:** Личные комментарии и личный чат ученика MUST быть отделены от
  общего обсуждения класса.

### Reactions and Day Chat

- **FR-COM-001:** Поля, комментарии и сообщения MUST поддерживать пять
  стандартных реакций.
- **FR-COM-002:** Участник с доступом к объекту MUST иметь возможность увидеть,
  кто оставил каждую реакцию.
- **FR-COM-003:** Чат MUST поддерживать root-сообщения и ответы любой глубины.
- **FR-COM-004:** Root-сообщение MUST становиться отдельной вкладкой только
  после появления хотя бы одного ответа.
- **FR-COM-005:** Интерфейс MUST показывать не более десяти наиболее недавно
  активных веток.
- **FR-COM-006:** Ветка, скрытая из-за лимита, MUST сохранять все сообщения и
  возвращаться во вкладки при новой активности.
- **FR-COM-007:** Общая вкладка MUST показывать все доступные пользователю
  сообщения; вкладка ветки — её root и всех descendants.

### Homework, Grades, and Attendance

- **FR-EDU-001:** Ученик MUST иметь возможность отметить своё ДЗ выполненным.
- **FR-EDU-002:** Teacher MUST оценивать ДЗ по шкале `α`, `β`, `γ`, `F`.
- **FR-EDU-003:** Статус выполнения ДЗ MAY видеть класс, но персональную оценку
  MUST видеть только соответствующие student/parent, назначенный teacher и
  admin.
- **FR-EDU-004:** Для MVP посещаемость MUST иметь состояния `present` и
  `absent`; опоздание или частичное присутствие не образует отдельного
  финансового состояния.
- **FR-EDU-005:** Отсутствовавшему ученику в индивидуальном или групповом
  классе стоимость урока MUST NOT начисляться.
- **FR-EDU-006:** Admin или назначенный teacher MAY исправить посещаемость.
  Исправление `absent` на `present` MUST создать начисление по исторически
  применимой цене, пересчитать баланс и оставить audit record; финансово
  значимое исправление MUST детерминированно пересчитать связанные начисления.
- **FR-EDU-007:** В конце урока назначенный teacher MUST открыть день урока в
  классе и увидеть список его учеников. Нажатие на знак «минус» слева от
  ученика MUST отметить этого ученика как `absent`; остальные ученики при
  сохранении отметки считаются `present`.

### Payments and Balance

- **FR-FIN-001:** Класс MUST иметь стоимость одного урока и сумму разового
  платежа по умолчанию.
- **FR-FIN-002:** Стоимость урока MAY быть переопределена для конкретного
  ученика; сумма по умолчанию редактируется в форме конкретного платежа.
- **FR-FIN-003:** Цена MUST фиксироваться в начислении урока; последующее
  изменение настройки влияет только на будущие начисления.
- **FR-FIN-004:** Платёж MUST содержать ученика, денежную сумму и фактическую
  дату.
- **FR-FIN-005:** Платёж MUST последовательно погашать самые старые непокрытые
  начисления ученика.
- **FR-FIN-006:** Полностью покрытый урок получает состояние `paid`; частично
  покрытый урок остаётся `overdue` с точным остатком; излишек становится
  авансом.
- **FR-FIN-007:** Непокрытое начисление проведённого и подлежащего оплате урока
  становится `overdue` сразу после завершения урока.
- **FR-FIN-008:** Отмена начисления или исправление посещаемости MUST
  детерминированно перераспределить существующие суммы по старейшим долгам и
  сохранить audit record.
- **FR-FIN-009:** Общий календарь класса MUST NOT использовать цвет для
  отображения оплаты. Личный календарь ученика MUST показывать `paid` и
  `overdue` состояния уроков.
- **FR-FIN-010:** Денежные расчёты MUST сохранять точные суммы без ошибок
  двоичного округления.
- **FR-FIN-011:** Admin MAY создать новый платёж для разрешённого ученика и
  класса собственного Center. Назначенный teacher MAY создать новый платёж
  только для ученика назначенного класса. Cross-center доступ MUST быть
  отклонён для всех ролей.
- **FR-FIN-012:** Только admin MAY исправить или отменить платёж для
  разрешённого ученика и класса собственного Center; teacher не может
  исправить или отменить платёж. Каждая такая операция MUST сохранить audit
  record с автором, временем и изменением.
- **FR-FIN-013:** Если фактическая дата платежа является учебным днём, его маркер
  в личном календаре MUST визуально размещаться на ближайшем предыдущем
  неучебном дне и MUST показывать фактическую дату.
- **FR-FIN-014:** Визуальное смещение маркера MUST NOT изменять фактическую дату
  Payment, баланс или Payment Allocation.
- **FR-FIN-015:** Несколько маркеров, попавших на один неучебный день, MUST
  сохраняться и быть доступны в компактном списке.

## Non-functional Requirements

### Privacy and Authorization

- **NFR-PRIV-001:** Любая server-side операция чтения или изменения MUST
  проверять роль, принадлежность к центру, классу и ученику; скрытие элемента в
  UI не считается контролем доступа. Admin ограничен membership собственного
  Center; cross-center доступ не разрешён.
- **NFR-PRIV-002:** Student и parent MUST NOT получать оценки, личные
  обсуждения или финансовые данные другого ученика.
- **NFR-PRIV-003:** До использования реальных данных role-based access MUST быть
  проверен негативными сценариями для каждой роли и личного контекста.
- **NFR-PRIV-004:** Назначенный teacher MAY читать всю историю класса и личных
  контекстов его учеников независимо от даты назначения; после снятия назначения
  доступ MUST прекратиться.
- **NFR-PRIV-005:** Статистические таблицы MUST возвращать только строки и поля,
  разрешённые серверно определённым role/membership scope: Admin — только
  собственного Center, Teacher — только назначенных классов. Student и Parent
  MUST NOT получать center-wide реестры, чужие финансовые статусы,
  посещаемость или личные связи через статистический маршрут.

### Financial Correctness

- **NFR-FIN-001:** Одинаковая последовательность уроков, посещаемости, цен и
  платежей MUST всегда давать одинаковый баланс и распределение.
- **NFR-FIN-002:** До использования реальных данных MUST быть проверены полная,
  частичная и избыточная оплата, изменение посещаемости и сохранение
  исторической цены.

### Usability and Accessibility

- **NFR-UX-001:** Оператор при финальном human review должен без открытия всех
  дней различать учебные и неучебные даты и понимать доступные состояния по
  сочетанию геометрии, подписи/символа и цвета.
- **NFR-UX-002:** Навигация между общим и личным календарями и точный переход по
  date picker не должны приводить пользователя в контекст другого ученика.

### Quality Gates

- **NFR-QA-001:** Для implementation task минимальный product-level DoD —
  успешный build и базовый smoke check, а также все более сильные проверки,
  обязательные по tier-policy, acceptance criteria или repository config.
- **NFR-QA-002:** До финальной демонстрации MUST пройти интегрированные
  functional, privacy/access и financial-correctness проверки.
- **NFR-QA-003:** Финальное принятие MVP выполняется явным фидбеком оператора.

## Data / Domain Model

- **Center:** отдельный scope учебного заведения с собственными
  пользователями, классами и данными; Admin имеет membership одного Center.
- **Educational Institution:** одно отображаемое название, настроенное для
  Center. Отдельное управление филиалами и несколькими центрами не входит в
  MVP.
- **Internal Account:** учётная запись приложения с назначенными ролями и
  membership.
- **External Identity:** уникальная Telegram или Google identity, привязанная к
  одному Internal Account.
- **Invitation:** одноразовое, ограниченное по времени право привязать provider
  к заранее созданному аккаунту.
- **Class:** режим обучения, участники, teacher, расписание и финансовые defaults.
- **Student Membership / Parent Link:** связь ученика с классом и родителя с
  учеником.
- **Lesson:** identity урока, запланированная/фактическая дата, состояние и
  общий материал.
- **Personal Lesson Context:** посещаемость, ДЗ, оценка, личные комментарии и
  обсуждение ученика.
- **Comment / Reaction / Message:** авторские объекты общения с границей общего
  или личного контекста.
- **Lesson Charge:** зафиксированная стоимость проведённого платного урока для
  конкретного ученика.
- **Payment:** сумма и фактическая дата внесения за ученика.
- **Payment Allocation:** воспроизводимая связь суммы платежа с начислениями.
- **Payment Marker:** календарная проекция Payment; её визуальная дата MAY отличаться
  от фактической даты, но не изменяет финансовые данные.
- **Audit Record:** история финансово значимого исправления.
- **Statistics Registry:** read-only представление разрешённых агрегированных
  данных об учениках, учителях или классах; оно не является отдельным источником
  истины и не изменяет исходные учебные, финансовые или аккаунтные записи.

## UX / Interaction Flow

### Initial Access

1. Оператор локально запускает bootstrap CLI, вводит email в интерактивном
   prompt и пароль в скрытом prompt и атомарно создаёт первого Admin с password
   credential в пустой базе.
2. Admin вводит email/password на странице входа.
3. Система проверяет credential, создаёт существующую server session и открывает
   защищённую Admin-поверхность без center membership.
4. Admin создаёт ровно один Center и задаёт ему одно название учебного
   заведения; система атомарно создаёт Admin membership и открывает управление
   этим Center.
5. Admin создаёт участников напрямую с email/password или выдаёт одноразовые
   invite-ссылки.
6. Пользователь приглашения выбирает Telegram или Google и подтверждает
   identity.
7. Система привязывает identity к заранее созданному аккаунту и открывает
   разрешённый контекст.
8. Уже авторизованный пользователь при необходимости добавляет второй provider
   из настроек профиля.

### Class Work

1. Пользователь открывает эластичный календарь класса.
2. Учебный день открывает общую форму урока.
3. В конце урока Teacher открывает день урока в классе, видит список учеников и
   ставит «минус» слева от каждого отсутствовавшего; остальные отмечаются как
   присутствовавшие.
4. Teacher заполняет материал, ДЗ и оценки.
5. Участники класса взаимодействуют через комментарии, реакции и чат в пределах
   своих прав.
6. Из календаря класса пользователь переходит к разрешённому личному календарю.

### Personal Context and Payment

1. Личный календарь показывает состояния ученика, включая оплату уроков.
2. Admin заносит платёж для разрешённого ученика собственного Center либо
   назначенный teacher заносит платёж для ученика своего класса, всегда с
   фактической датой.
3. Система погашает старейшие долги и показывает новый баланс.
4. Если платёж внесён в учебный день, личный календарь показывает маркер на
   ближайшем предыдущем неучебном дне и подписывает фактическую дату.
5. Исправление посещаемости или начисления пересчитывает баланс с audit record.

### Global Navigation and Statistics

1. Авторизованный пользователь открывает hamburger-меню на любой защищённой
   странице.
2. Пользователь выбирает «Главная», «Классы», «Статистика», «Профиль» или
   «Выйти».
3. При выборе «Классы» система показывает доступный пользователю список
   классов.
4. При выборе «Статистика» пользователь выбирает реестр учеников, учителей или
   классов.
5. Пользователь нажимает заголовок столбца, чтобы включить сортировку; текущий
   порядок виден в заголовке.
6. Сервер проверяет роль и scope до формирования таблицы; недостаток доступа
   даёт отказ или безопасное отсутствие раздела без выдачи чужих строк.

7. Пункт «Главная» открывает роль-ориентированный стартовый экран: Admin — его
   Center и классы, Teacher — список назначенных классов, Student и Parent —
   календарь доступного класса.

## Integrations / Dependencies

- Telegram Login для подтверждения Telegram identity.
- Google OAuth для подтверждения Google identity.
- Оба provider являются внешними зависимостями; их отказ MUST завершаться
  явной ошибкой без изменения ролей, membership или привязок.
- Конкретные libraries, storage, deployment и provider SDK принадлежат
  downstream architecture design, а не PRD.

## Edge Cases / Failure Handling

- Повторное использование, отзыв или истечение invitation не создаёт аккаунт и
  не меняет существующую привязку.
- Попытка привязать provider identity, уже связанную с другим аккаунтом,
  отклоняется без автоматического merge.
- Сбой provider callback не создаёт частично привязанный аккаунт.
- Неизвестный email и неверный пароль возвращают одинаковый generic отказ и не
  создают сессию; bootstrap в непустой базе или duplicate normalized email
  оставляет account/credential state неизменным.
- Удалённый из класса пользователь немедленно теряет доступ к его общим и личным
  данным, но авторские записи сохраняют атрибуцию согласно дальнейшей data
  policy.
- Новый teacher получает полную прошлую историю класса с момента назначения; снятие
  назначения немедленно закрывает ему дальнейшее чтение.
- Отмена или перенос урока не должны незаметно дублировать начисление.
- Повторная отправка финансовой команды не должна создавать второй платёж без
  нового явного подтверждения.
- Частичная оплата сохраняет точный остаток, а аванс не теряется.
- Если ближайший предыдущий неучебный день находится в предыдущей неделе или месяце,
  маркер размещается там и остаётся доступен при навигации к этой дате.
- Скрытая вкладка чата не означает удаление ветки.
- Если у пользователя нет доступных классов или записей статистики, система
  показывает пустое состояние без чужих данных.
- Отозванный membership или assignment MUST закрыть ранее доступные классы и
  статистические строки при следующем запросе.
- Выход MUST сделать защищённые страницы недоступными по старой сессии.

## Acceptance Criteria

- **AC-AUTH-001:** По одной invite-ссылке можно привязать ровно один внутренний
  аккаунт через выбранный Telegram или Google provider; роль берётся только из
  приглашения.
- **AC-AUTH-002:** Второй provider добавляется к тому же аккаунту только из
  подтверждённой сессии; повторно использованная identity не создаёт дубль.
- **AC-AUTH-003:** Локальная CLI в пустой базе атомарно создаёт первого Admin и
  его unique normalized email/password credential; скрытый prompt не допускает
  пароль в argv/log, plaintext не сохраняется, а успешный browser login создаёт
  существующую server session. Неверный email/password даёт generic отказ без
  сессии.
- **AC-AUTH-004:** Admin может атомарно создать teacher, student или parent с
  email/password и войти через существующий `/login`; для parent сохраняется
  выбранная student link.
- **AC-CAL-001:** Неделя отображает учебные дни шире неучебных, а date picker
  приводит к выбранной дате.
- **AC-DAY-001:** Общие поля урока видны классу, а личные оценки, финансы и
  обсуждения недоступны другим ученикам и родителям.
- **AC-COM-001:** Ответ создаёт вкладку ветки; после превышения десяти вкладок
  скрывается наименее недавно активная без потери сообщений.
- **AC-EDU-001:** Статус ДЗ виден классу, оценка — только разрешённым участникам.
- **AC-EDU-002:** `absent` не создаёт начисление; исправление на `present`
  создаёт его по исторически применимой цене, пересчитывает баланс и оставляет
  audit record.
- **AC-FIN-001:** Платёж закрывает старейшие долги, корректно сохраняет
  частичный остаток и аванс.
- **AC-FIN-002:** Изменение текущей настройки цены не меняет уже созданные
  начисления.
- **AC-FIN-003:** Teacher может создать платёж только для своего класса и не может
  его исправить/отменить; admin может, а изменение видно в audit record.
- **AC-FIN-004:** Платёж в учебный день показан на ближайшем предыдущем неучебном дне с
  подписью фактической даты; сам Payment и его allocation не изменены.
- **AC-PRIV-001:** Негативные role/membership проверки подтверждают отказ в
  любом неразрешённом cross-class, cross-student и cross-center доступе.
  Admin видит статистику и выполняет операции только в собственном Center;
  Teacher остаётся ограничен назначенными классами для статистики и создания
  платежей и не может исправлять или отменять платежи.
- **AC-PRIV-002:** После назначения teacher видит старые учебные данные, личные комментарии
  и чат класса; после снятия назначения повторный доступ отклоняется.
- **AC-NAV-001:** На каждой защищённой странице открывается единое меню с
  главной, доступными классами, статистикой, профилем и выходом; выход завершает
  сессию.
- **AC-STAT-001:** Разрешённый пользователь может открыть три статистических
  реестра, а таблицы содержат согласованный оператором набор столбцов для
  учеников, учителей и классов.
- **AC-STAT-002:** Таблица учителей переносит каждый следующий класс на новую
  строку и сортирует по первому классу.
- **AC-STAT-003:** Каждый столбец можно отсортировать в обоих направлениях, а
  активное направление понятно по заголовку; текст сортируется по алфавиту,
  даты — хронологически, проценты и числа — численно.
- **AC-STAT-004:** Запрос статистики с ролью или scope без доступа не раскрывает
  строки другого центра, класса, ученика или родителя.
- **AC-STAT-005:** Добавление меню и статистики не меняет существующие сценарии
  календаря, уроков, личного контекста и финансового ledger.
- **AC-HOME-001:** Пункт «Главная» открывает собственный Center и его классы
  для Admin, список назначенных классов для Teacher и календарь доступного
  класса для Student/Parent.
- **AC-EDU-003:** В конце урока Teacher может открыть день урока, увидеть всех
  учеников и отметить отсутствующих знаком «минус»; сохранённые отметки влияют
  на посещаемость и связанные начисления.
- **AC-STAT-006:** Процент платёжеспособности считает долю своевременно
  оплаченных Payment Allocation среди всех allocations к lesson charges; аванс
  и нераспределённая часть не считаются. Allocation с датой до фактической даты
  урока считается своевременным. При отсутствии платежей
  отображается `0%`, а при своевременной оплате всех платежей — `100%`.
- **AC-MVP-001:** После обязательных integrated checks оператор просматривает
  работающий MVP и явно принимает его либо возвращает замечания.

## Verification Strategy

- Build и smoke flow для основных маршрутов каждой роли.
- Integration tests для invitation/provider binding и негативных access cases.
- Scenario tests денежного ledger: точная, частичная, избыточная оплата,
  отсутствие и последующая корректировка.
- Role-based проверки общего и личного контекста.
- Human review оператора для эластичного календаря, ясности состояний и
  финального принятия MVP.
- Browser smoke для открытия меню на нескольких защищённых страницах, переходов
  и выхода.
- Role-based integration/browser checks для доступного списка классов,
  статистических реестров, cross-scope отказов и сортировки каждого столбца.
- Применимые tier-gates и evidence requirements остаются обязательными.
