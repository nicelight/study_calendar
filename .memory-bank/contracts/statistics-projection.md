# Statistics Projection Contract

## Purpose and ownership

The Statistics Projection is a read-only view composed for FT-007. Lesson
Context owns the cross-slice composition and exposes only serializable
projection data to the SvelteKit route. It does not persist a statistics table
or become a source of truth.

Provider ownership remains explicit:

- Identity & Access owns participant `fullName` and immutable `registeredAt`.
- Center & Scheduling owns Center, Class, membership, parent-link, teacher
  assignment, and institution facts and resolves registry scope.
- Learning Progress owns attendance facts and computes attendance percentages.
- Financial Ledger owns charges, payments, allocations, and computes payment
  capability.

Routes, page components, and the composition root MUST NOT read provider tables
directly or implement these provider-owned formulas.

## Participant profile metadata

- The canonical creation, ownership, current-actor, and scoped-query contract is
  [.memory-bank/contracts/access-control.md#account-profile-facts](access-control.md#account-profile-facts).
- `fullName` is a required trimmed display value for participant accounts and is
  returned only where the caller's server-resolved scope permits it.
- `registeredAt` is generated by the server when the account is created and is
  immutable after creation.
- Lesson Context obtains these fields through the Identity & Access Actor
  Context Boundary for account IDs already scoped by Center & Scheduling; no
  statistics code may read Identity & Access tables directly.
- The target account population is created with mandatory surname and given
  name. This feature adds no migration, backfill, or legacy-account behavior.
- Profile metadata is not client-supplied authority and does not change role,
  membership, assignment, or authentication behavior.

## Registry projection boundary

The authorized registry projection returns three read-only collections:

- Students: full name, registration date, class names, linked parent names,
  assigned teacher names, payment capability percentage, attendance
  percentage, and institution name.
- Teachers: full name, registration date, assigned class names, attendance
  percentage, institution name, and student count across assigned classes.
- Classes: class name, institution name, student count, and assigned teacher
  names.

Admin receives only rows for the Admin's own Center. Teacher receives only rows
for assigned classes. Student and Parent MUST be denied the center-wide
registry projection; a denial MUST NOT reveal unrelated row existence or
private fields.

The result MUST be read-only and MUST NOT mutate account, Center, Class,
membership, assignment, lesson, attendance, payment, allocation, balance, or
audit facts.

## Center and Scheduling registry facts query

Center & Scheduling exposes the scoped structural input to the registry
projection. For a server-resolved Admin it returns only own-Center rows; for a
Teacher it returns only assigned-class rows; Student and Parent requests are
denied without revealing row existence. The result contains authorized account
IDs plus Center & Scheduling-owned institution, class, membership, parent-link,
teacher-assignment, and count facts.

This query MUST NOT call Identity & Access, return `fullName` or `registeredAt`,
compute attendance or payment metrics, or compose the final registry payload.
Lesson Context first obtains these scoped facts, then calls the accepted Actor
Context, Personal Progress, and Financial Projection boundaries. Repeated
queries are read-only and leave Center & Scheduling state unchanged.

## Attendance percentage query

For a student, attendance percentage is:

`present conducted student/lesson slots / all conducted student/lesson slots * 100`

The denominator includes every conducted lesson for the student's class,
including slots represented by the Teacher class-day attendance form. The
default-present workflow supplies `present` for an unmarked student slot at
attendance submission; an explicit `absent` is counted as absent. A correction
from `absent` to `present` is reflected by the next read without the projection
writing attendance.

For a Teacher, attendance percentage is the same ratio aggregated across all
conducted student/lesson slots in that Teacher's assigned classes. No teacher
attendance fact is invented or persisted by this projection.

With no conducted slots, the percentage is `0%`. The provider returns a numeric
percentage suitable for numeric sorting; the UI appends the percent sign.

## Payment capability query

For a student, payment capability is:

`counted on-time Payment Allocations / all counted Payment Allocations * 100`

An allocation is on time only when its Payment's factual date is strictly
earlier than the actual lesson date of the allocated Charge. Cancelled or
otherwise non-counted financial facts follow the Financial Ledger projection
contract. Advance and unallocated payment amounts are excluded because they
are not Payment Allocations to a lesson Charge.

With no counted allocations, the value is `0%`. `100%` means every counted
allocation is on time. The query MUST reuse Financial Ledger-owned facts and
MUST NOT mutate payment, allocation, charge, balance, or audit state.

## Sorting and presentation

Every registry column supports ascending and descending sorting. The active
direction MUST be visible in the column header. Text uses alphabetical order,
dates chronological order, and percentages/counts numeric order. A Teacher's
multiple classes render one per line; sorting that column uses the first class
in the rendered ordered list.

Sorting is a presentation operation over the authorized result and MUST NOT
change server-side scope or provider query semantics.

## Failure and verification target

Unauthenticated, revoked, cross-center, unassigned-teacher, and
student/parent center-wide registry requests are denied before unrelated data
is returned. A removed assignment is denied on the next server-side check.
Projection reads are safe to repeat and leave state-before equal to state-after.

Verification covers profile metadata persistence, role/scope matrices, guessed
route denial, all registry fields, both sort directions and types, first-class
teacher sorting, no-payment/on-time/overdue/mixed/boundary-date payment cases,
no-slot/explicit-absence/default-present/correction attendance cases, and
non-mutation of provider facts.
